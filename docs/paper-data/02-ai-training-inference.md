# 2. AI Training & Inference Data

## 2.1 Accuracy & confusion matrix: ROC, precision, recall, FP/FN rate

**Measured** on 2026-09-06 against commit `3746a89`, via a new evaluation
script written for this purpose,
[`cmd/ai-engine/scripts/evaluate_model.py`](../../cmd/ai-engine/scripts/evaluate_model.py)
(reproduce with `python scripts/evaluate_model.py` from `cmd/ai-engine/`).

Context the numbers need to be read against: `sentinel_ai/model.py`'s
autoencoder is **unsupervised** — it only ever trains on "normal" traffic
and has no labels in production. The only labels that exist anywhere are in
the synthetic dataset generator
(`scripts/generate_synthetic_dataset.py`), so this is a synthetic-data
evaluation, not a real-traffic one — consistent with `ROADMAP.md` Phase 1
still listing "replace the synthetic training dataset with real traffic" as
open work. Train/evaluation split is disjoint (3200 normal samples to
train, 800 held out, never seen during training) so the numbers are not
measuring memorization.

**Method:** `Autoencoder` trained for 200 epochs on 3,200 synthetic-normal
samples (seed 42); reconstruction-error threshold calibrated the same way
production does (`ScoringEngine`: 99th-percentile training error ×4,
clipped to `[0,1]`); scored the 800 held-out normal samples plus 200
synthetic-anomalous samples (signaling storms, malformed framing, off-hours
scans — see 2.3).

**Read honestly:** zero false positives at every production threshold on
*this* dataset is a property of how separable the synthetic anomalous

why recall (which one is caught) is the more informative column here than
precision, and why `ROADMAP.md` Phase 1 makes real-traffic validation of
the sensitivity thresholds an explicit open item, not a formality.

## 2.2 Score differential: real normal vs. signaling-storm traffic

**Measured** on 2026-09-06 against a live Open5GS+UERANSIM core running in
this machine's WSL2 environment (see
`memory/wsl2_real_test_environment.md`) — not the recalled session-log
number originally referenced (that lived only in a separate, unreachable
background session's terminal transcript); this is a freshly captured,
independently reproducible replacement instead.

**Method:** two real GTP-U captures via `tcpdump -i lo 'udp port 2152'`
(`upf.yaml` confirms Open5GS's N3 interface is loopback `127.0.0.7`):
- `normal.pcap` — 30 packets over 29.7s (~1 pkt/s), from a baseline `ping
  -I uesimtun0` through the live PDU session.
- `storm.pcap` — 618 packets over 9.99s (~62 pkt/s), from `ping -f` (flood
  ping) through the same tunnel — a real, if modest, signaling-rate spike.

Both pcaps are committed alongside this file
(`docs/paper-data/normal.pcap`, `storm.pcap`, plus the raw `tcpdump -tt -n`
text dumps used to drive the scorer). They were scored by
[`cmd/ai-engine/scripts/score_real_capture.py`](../../cmd/ai-engine/scripts/score_real_capture.py)
(reproduce with `python scripts/score_real_capture.py` from `cmd/ai-engine/`),
which re-derives each packet's `rate_per_second` by reimplementing
`bpf/packet_filter.c`'s exact 1-second sliding-window `track_signal_rate`
logic against the pcap's real per-packet timestamps, then scores the
resulting `NormalizedEvent`s through the actual production
`extract_features`/`ScoringEngine` code and the real trained
`cmd/ai-engine/models/autoencoder.onnx` (2026-09-05) — the same model and
code path as production, run directly rather than round-tripped through
NATS/the operator for this measurement.

| Window | Packets | Duration | Observed rate | Peak 1s window count | Score (min/mean/max) |
|---|---|---|---|---|---|
| Normal | 30 | 29.70s | 1.01 pkt/s | 1 | 0.0899 / 0.0899 / 0.0899 |
| Storm | 618 | 9.99s | 61.85 pkt/s | 63 | 0.0902 / 0.0903 / 0.0904 |

**Read honestly — this is a real but modest differential, and that itself
is a finding, not a disappointing result to smooth over:** the model
(trained only on the synthetic dataset — see 2.3) learned "storm" as
rate ≈ 800–4500/s (`generate_synthetic_dataset.py`'s `_anomalous_event`).
A real flood ping through this WSL2 tunnel only reaches ~62 pkt/s — real,
but roughly an order of magnitude below the synthetic training
distribution's storm range — so the production model barely reacts to it.
This directly reinforces `ROADMAP.md` Phase 1's open item: the synthetic
dataset's anomaly thresholds have not yet been validated against what a
real attacker/real network conditions actually produce, and this
measurement is the first concrete data point showing the gap rather than
assuming it away.

## 2.3 Dataset evolution: synthetic distributions and real captures

**Synthetic dataset** (`cmd/ai-engine/scripts/generate_synthetic_dataset.py`,
sourced verbatim from the code — this is not a claim about real-world
attack distributions, and the module's own docstring says so explicitly):

- **Normal traffic:** protocol uniformly chosen from `GTP-U`/`SIP`/`SMPP`/
  `HTTP2`; payload size `~N(256, 64)` bytes; rate `~N(20, 8)`/s; spans the
  full 24h day uniformly (deliberately — see the code comment: a narrow
  time slice would let the model key on "wrong time of day" instead of the
  protocol/rate/malformed signals every other event type is meant to be
  judged on).
- **Anomalous traffic**, three kinds chosen uniformly at generation time:
  - *storm*: real GTP-U/SIP protocol/port, rate `U(800, 4500)`/s (40-225×
    normal).
  - *malformed*: any protocol, payload size `U(0, 8)` bytes, `malformed=True`
    flag set (parser-detected framing failure).
  - *scan*: `UNKNOWN` protocol, random high port, rate `U(200, 1000)`/s,
    deliberately clustered 02:00-04:00 — chosen to overlap the hours a few
    normal samples also naturally land in, so the model has to weigh
    time-of-day jointly with the other features rather than using either
    signal alone.
- Default generation size: 4,000 normal / 200 anomalous samples (seed 42,
  reproducible — `python scripts/generate_synthetic_dataset.py`).

**Real captures (PCAP):** now exist — `docs/paper-data/normal.pcap` and
`storm.pcap` (2.2 above), the first real PCAP pair this project has. The
earlier WSL2 real-traffic validation rounds (500+500 packet UDP burst; the
6-ICMP PDU-session run) generated genuine on-wire GTP-U/SIP/ICMP traffic
and proved the capture→scoring pipeline against it, but neither wrote a
`tcpdump` capture to disk — only `bpftool map dump` counts and NATS event
logs were captured. These two are 4.7KB/97KB respectively — real but small;
growing this into an actual replacement training set (per `ROADMAP.md`
Phase 1) needs materially more volume and traffic-shape variety (multiple
UEs, real attack tooling rather than `ping -f`, SIP alongside GTP-U) than a
single flood-ping session provides.
